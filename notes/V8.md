# Движок V8 — Конспект

## Что такое V8

**V8** — это JavaScript-движок, разработанный Google.

Используется в:

- Google Chrome
- Node.js

Основная задача V8 — выполнять JavaScript-код максимально быстро, преобразуя его в машинный код.

---

# Этапы преобразования JavaScript в V8

## 1. Парсинг (Parsing)

Исходный JavaScript-код разбирается парсером.

```js
const x = 5;
```

Результатом является AST.

---

## 2. Построение AST

AST (Abstract Syntax Tree) — абстрактное синтаксическое дерево.

Пример:

```text
VariableDeclaration
 └── Identifier(x)
 └── Literal(5)
```

AST представляет структуру программы в удобном для анализа виде.

---

## 3. Генерация Bytecode

Компонент **Ignition** преобразует AST в байт-код.

```text
LdaSmi [5]
Star r0
Return
```

Bytecode — промежуточное представление между JavaScript и машинным кодом.

---

## 4. Выполнение Bytecode

Ignition начинает выполнять сгенерированный байт-код.

На этом этапе код уже работает.

---

## 5. Компиляция в Machine Code

Если участок кода часто выполняется (hot code), V8 компилирует его в машинный код.

Для этого используются:

- Sparkplug
- TurboFan

---

# Архитектура V8

Основные компоненты:

## Parser

Разбирает JavaScript-код и строит AST.

```text
JS Code
   ↓
 Parser
   ↓
 AST
```

---

## Ignition

Интерпретатор V8.

Задачи:

- получает AST;
- генерирует bytecode;
- выполняет bytecode.

```text
AST
 ↓
Ignition
 ↓
Bytecode
```

---

## Sparkplug

Baseline-компилятор.

Задачи:

- быстро компилирует bytecode в machine code;
- практически не выполняет сложных оптимизаций.

Плюс:

- быстрый запуск приложения.

```text
Bytecode
 ↓
Sparkplug
 ↓
Machine Code
```

---

## TurboFan

Оптимизирующий компилятор.

Задачи:

- анализирует часто используемый код;
- выполняет оптимизации;
- генерирует максимально быстрый machine code.

```text
Hot Code
 ↓
TurboFan
 ↓
Optimized Machine Code
```

---

# Полный путь выполнения кода

```text
JavaScript
     ↓
   Parser
     ↓
     AST
     ↓
  Ignition
     ↓
  Bytecode
     ↓
  Sparkplug
     ↓
 Machine Code
     ↓
  TurboFan
     ↓
 Optimized Machine Code
```

---

# Деоптимизация (Deoptimization)

## Что это

Откат от оптимизированного машинного кода к менее оптимизированному исполнению.

Обычно:

```text
Optimized Machine Code
        ↓
     Deopt
        ↓
Bytecode / Baseline Code
```

---

## Почему происходит

TurboFan строит оптимизации на предположениях.

Например:

```js
function sum(a, b) {
  return a + b;
}
```

Если функция долго вызывается только с числами:

```js
sum(1, 2);
sum(5, 6);
```

TurboFan оптимизирует её под числа.

Но затем:

```js
sum("a", "b");
```

Предположение ломается.

Происходит деоптимизация.

---

# Управление памятью в V8

V8 использует Heap (кучу) для хранения объектов.

---

# Поколения памяти

Heap делится на два поколения.

## Young Generation

Молодое поколение.

Содержит:

- недавно созданные объекты;
- краткоживущие объекты.

Большинство объектов умирает именно здесь.

---

## Old Generation

Старое поколение.

Содержит:

- объекты, пережившие несколько сборок мусора;
- долгоживущие данные.

---

# Очистка Young Generation

Используется алгоритм:

## Scavenge GC

Основан на:

- Copying Collector
- Semi-Space Collector

---

### Принцип работы

Память делится на:

```text
From Space
To Space
```

Пример:

```text
From Space
 ├─ Obj A (жив)
 ├─ Obj B (мусор)
 └─ Obj C (жив)
```

Во время GC:

```text
To Space
 ├─ Obj A
 └─ Obj C
```

Живые объекты копируются.

Оставшаяся память очищается целиком.

---

# Mark-Sweep

Основной алгоритм очистки памяти для старого поколения.

---

## Шаг 1. Root Traversal

Поиск корневых ссылок:

- Global Object
- Stack
- Closures

```text
Roots
 ↓
Object A
 ↓
Object B
```

---

## Шаг 2. Mark

Все достижимые объекты помечаются как живые.

```text
A ✔
B ✔
C ✔
```

---

## Шаг 3. Sweep

Все непомеченные объекты удаляются.

```text
D ✖
E ✖
F ✖
```

---

## Шаг 4. Reset Marks

Сбрасываются отметки для следующего цикла GC.

---

# Three-Color Marking (3ColorMark)

Улучшение алгоритма Mark-Sweep.

---

## White

Объект ещё не посещён.

Считается потенциальным мусором.

```text
White = неизвестен
```

---

## Gray

Объект найден, но его ссылки ещё не обработаны.

```text
Gray = найден
```

---

## Black

Объект полностью обработан.

Все его ссылки уже просмотрены.

```text
Black = проверен
```

---

# Работа алгоритма

Начальное состояние:

```text
White White White White
```

GC находит корневые объекты:

```text
Gray White White White
```

Обрабатывает ссылки:

```text
Black Gray White White
```

Далее:

```text
Black Black Gray White
```

В конце:

```text
Black Black Black White
```

---

## Что удаляется

Все объекты, оставшиеся белыми:

```text
White → Garbage
```

Они считаются недостижимыми.

---

# Краткая шпаргалка

## Архитектура

- Parser → строит AST
- Ignition → генерирует и выполняет bytecode
- Sparkplug → быстро компилирует bytecode в machine code
- TurboFan → генерирует оптимизированный machine code

---

## Путь выполнения

```text
JS
 ↓
Parser
 ↓
AST
 ↓
Ignition
 ↓
Bytecode
 ↓
Sparkplug
 ↓
Machine Code
 ↓
TurboFan
 ↓
Optimized Machine Code
```

---

## Deoptimization

Откат:

```text
Optimized Code
 ↓
Bytecode / Baseline Code
```

Причина:

- неверные предположения оптимизатора.

---

## Память

### Young Generation

- новые объекты;
- алгоритм Scavenge GC.

### Old Generation

- долгоживущие объекты;
- алгоритм Mark-Sweep.

---

## Mark-Sweep

1. Root Traversal
2. Mark
3. Sweep
4. Reset Marks

---

## Three-Color Marking

- White — не посещён
- Gray — найден, но не обработан
- Black — полностью обработан

Переход:

```text
White → Gray → Black
```

Белые объекты удаляются.
